## 0. 一句话结论

这份文档是一份**完整产品愿景**（等价于一个自适应学习平台的 PRD），不是一次能做完的迭代。
按全文落地，单人全职约 **8–12 个月**；现有英语模块可复用约 **30–40%**，**引擎层几乎从零建**。

需求里最有价值的一条是第三章「禁止为三个阶段分别复制三套系统」——这条我完全赞同，也是唯一必须现在就锁死的架构原则。

## 1. 需求本质：三层皮

| 层   | 内容                                         | 性质                   |
| ---- | -------------------------------------------- | ---------------------- |
| 表层 | 小学 1–6 + 初中 7–9 + 高中 1–3 的数学知识树  | 内容工作量，可增量填充 |
| 中层 | 10 个引擎 + 14 种题型 + 17 个可视化组件      | 真正的工程量主体       |
| 底层 | 自适应闭环：会什么 / 不会什么 / 下一步学什么 | 产品灵魂，也最难验证   |

绝大多数人会被表层（"把知识点录进去"）吸引，但成本全在中层。

## 3. Phase 0 四象限（需求第五十一章要求）

### A. 可直接复用（不动）

- `subjects` → `learning_paths` → `textbooks` → `semesters` → `chapters` → `knowledge` 六层数据模型
- `resetAndImport` 的 upsert 导入机制（8/28 已修复为多学科，实测幂等）
- `subjectResolver` + `config/subjects.ts` 的学科 UI 配置驱动
- 学习页 / 章节页 / 详情页 的渲染骨架
- 收藏、学习记录、复习（SRS）、游戏记录 的用户数据集合
- `memory-result` 统一结果页 + `gameResultStore`
- 速算游戏 `math-drill`（8/27 已交付）

### B. 需要抽象（改造，非重写）

| 目标                             | 怎么改                                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------------------ |
| `curriculumVersion` 提为一等字段 | 从 `textbook.name` 里拆出版本，新增字段，保留旧字段兼容                                          |
| `stage` / `grade` 提为一等字段   | 现状靠册次名反推，需显式化（需求第四章明确要求）                                                 |
| 掌握度 0–100                     | 在 `LearningState` 之外**并存** `masteryScore`，不删旧枚举                                       |
| 测试引擎可组卷                   | `TEST_PAPER_CONFIG` 从"固定配比"改为"规则驱动"，默认值保持 10 题不变（保英语）                   |
| 小游戏统一接口                   | `math-drill` 抽出 `MathGame` 接口（start/pause/resume/submit/reset/getResult），其余游戏逐步对齐 |

### C. 数学新增（从零建）

引擎 6 个：Knowledge Graph、Question Engine、Mastery Engine、Wrong Question Engine、Adaptive Test、Recommendation。
（Curriculum / Lesson / Reward / AI Tutor 建议延后，理由见第 4 节。）

数据集合建议新增 6 个：`knowledge_relations`、`questions`、`question_sets`、`user_mastery`、`user_wrong_questions`、`learning_events`。
（需求第四十四章列了 17 张表，但明确要求"不要无意义复制英语表"——上面 6 张是刚需，其余等用到再加。）

可视化组件 17 个 → **建议第一批只做 4 个**：`NumberLine`（数轴）、`FractionModel`（分数）、`CoordinatePlane`（坐标/函数图）、`GeometryCanvas`（几何拖拽）。这 4 个能覆盖小学分数/初中函数/初中几何三大块。

### D. 禁止改动（红线）

- 英语的 1214 词 + 发音 URL + 24 语法点数据
- `resetAndImport` 的 upsert 语义（保 id 稳定，用户数据跨导入存活）
- `LearningState` 状态机（只能加 `masteryScore`，不能删枚举）
- `TEST_PAPER_CONFIG` 默认配比（英语依赖它）

## 4. 五个必须你拍板的决策

### 决策 1：高中砍不砍？——**我建议 V1 砍掉**

- 现状高中内容为 0，且高中有 立体几何 3D、导数、解析几何——**可视化最重、AI 最容易讲错**的部分。
- 需求自己也说（第四十八章）"设计完整 ≠ 第一天填完"，第四十九章让"先把代表性知识点跑通"。
- 砍高中可省掉约 **40% 工作量**，且不影响架构（阶段是数据，随时可加）。

### 决策 2：AI 数学老师走不走云端付费 API？——**这里有硬冲突，必须先摊开**

- 项目里**完全没有 AI 接口**，从零建。
- 但你长期明确的偏好是「强烈偏好本地执行、厌恶付费云端 credit（包括零积分口号但实际走云的方案）」。
- **AI Tutor 必然要调云端大模型 API，必然花钱。** 这是无法绕开的矛盾。
- 折中建议：**V1 先做"程序化提示"**——题目自带 `hints` 字段（分级提示：轻提示 → 分步 → 完整讲解），**零 API 成本、零幻觉风险**，体验上已经能顶住需求第三十八章 80% 的场景（"只提示一步""再简单一点""举个例子"）。真 LLM 留到 V2，届时再定预算。

### 决策 3：可视化做几个？

17 个全做 ≈ 单人 4–6 个月。建议第一批 4 个（见 3.C），跑通后再批量复制模式。

### 决策 4：题库从哪来？——**版权红线**

- 需求第二十八章自己写明"不得直接抓取盗版题库"。
- 可行路径：AI 生成 + **程序二次验证**（需求第三十九章也这么要求）。
- 但"程序验证器"本身是工作量：方程求解器、几何约束检查、数值比对。
- 建议：先在**可判定题型**上做（四选一、填空数字、方程步骤），这些程序能 100% 验证；证明题/综合题延后。

### 决策 5：是否现在就重构数据模型加 `stage/grade/curriculumVersion`？

- 现在改成本最低（数据还没铺开）。等录了几千条知识点再改就是灾难。
- 建议**现在就加**，但用"新增字段 + 旧字段保留"的兼容方式，不动英语。

## 5. 三个方案（含工作量）

|        | 方案 A 全量                 | **方案 B 推荐**           | 方案 C 最小闭环                     |
| ------ | --------------------------- | ------------------------- | ----------------------------------- |
| 范围   | 需求全文，含高中            | 小学+初中，砍高中与真 LLM | 1 个年级 × 3 个知识点跑通全链路     |
| 引擎   | 10 个                       | 6 个                      | 4 个（Question/Mastery/Wrong/Test） |
| 可视化 | 17 个                       | 4 个                      | 1–2 个                              |
| AI     | 真 LLM                      | 程序化 hints              | 无                                  |
| 工作量 | 8–12 人月                   | **3–4 人月**              | 3–4 周                              |
| 风险   | 高（内容量、AI 成本、质量） | 中                        | 低                                  |
| 产出   | 完整产品                    | **可用的数学学科**        | 架构验证                            |

**我的推荐：先 C 后 B。**
即用 3–4 周把「一个年级、三个知识点」的完整闭环（学习 → 可视化 → 练习 → 测试 → 错因 → 补弱 → 掌握度）真正跑通，验证架构站得住；然后按 B 的范围批量填充。
这也正是需求第四十八章/第五十一章作者本人的策略（"先把代表性知识点跑通所有交互模板，然后批量填内容"）。

## 6. 如实登记的缺口与风险

1. **验收目标无法测试**——需求第五十二章"系统是否知道这个学生哪里不会，并能把他教会"是感觉，不是指标。需要改成可量化验收（如：掌握度预测准确率、错题修复率）。
2. **掌握度公式若不验证就是玄学**——需求第三十四章列了 10 个影响因素，但没有权重、没有验证方法。建议 V1 先用简单可解释版本（首次正确率 + 近期表现 + 间隔复习），跑出数据再调。
3. **高中内容 0 起步**，且是最难部分。
4. **AI 成本与你的本地优先偏好冲突**（决策 2）。
5. **题库版权**：不能用现成真题，只能自研 + 程序验证。
6. **我 8/27 生成的 293 个数学概念是 AI 骨架**，需要教师校对；且当时只做到初中，没有高中。
7. `learning-path.ts` 仍硬编码 `语法`/`词汇`，数学缺"偏好直达"快捷键（已知小债）。
